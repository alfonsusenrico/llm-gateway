# Proposal

## Why

Nothing can call the gateway until a project can be registered and can prove
who it is.

Contract files on disk keep no history and are prone to permission and
reload problems. Splitting control between contracts, project settings, and
gateway settings leaves no single place to see what a project may do. Slow
password hashes add CPU cost without adding security for random keys. This
change defines contract version 1 as data the gateway owns, along with
per-environment project keys designed for a gateway that will be publicly
reachable.

## Expected Outcome

- The owner registers a project with one command, or through the interactive
  admin menu, and receives a development key and a production key, each shown
  once.
- A request carrying a valid key is identified as that project and
  environment. A malformed, unknown, revoked, or wrong key is refused with a
  stable problem code.
- Repeated failures from one source are throttled, and the owner is alerted.
- Every contract edit is kept as a version that the owner can list, show, and
  export.

## What Changes

- **Contract version 1, stored in Postgres with full version history.** It
  holds:
  - the project ID and display name;
  - its status;
  - a request per environment: requests per minute, concurrency, monthly
    budget, and per-call cost ceiling;
  - model profiles.
- **Validation before save:** an invalid contract is never stored. Loading
  validates again and quarantines any row that fails.
- **Project API keys:**
  - format `lgw.<env>.<key_id>.<secret>`;
  - one active key per project and environment;
  - stored as HMAC-SHA256 with a gateway-held pepper;
  - rotation with an optional grace period;
  - revocation.
- **Request authentication:** a bearer key, checked for format before any
  database lookup, compared in constant time, with failed attempts throttled
  per source address and an owner alert on repeated rejection.
- **`GET /v1/projects/self`:** returns the authenticated project's ID,
  environment, and contract version, so a client can check its credentials.
- **Admin CLI subcommands:**
  - `project register`, `list`, `show`, `history`;
  - `set-request`, `set-profile`, `remove-profile`;
  - `enable`, `disable`;
  - `rotate-key`, `revoke-key`;
  - `export`, `import`.
- **Interactive menu:** `llm-gateway-admin` with no arguments opens a menu
  over the same actions. It loops until `0` or Ctrl+C.

## Non-goals

- Grants and enforcement. Allocation is the next change; budget and rate
  enforcement come in phase 2.
- Validating profiles against a model catalogue (phase 2). Profiles are
  checked for structure only.
- Fields for call modes, hosted tools, and input limits. Each is added, as
  an optional additive field, by the phase that gives it meaning.
- Browser login, or user identities inside projects.

## Capabilities

### New Capabilities

- `project-contracts`: the contract version 1 data model, validation,
  versioned history, status, and the owner's registry operations.
- `project-authentication`: project API key format, issuance, storage,
  rotation, revocation, request authentication, and failed-attempt
  throttling.

### Modified Capabilities

None.

## Impact

- **Capability:** `api-consumers` becomes active through the first
  authenticated endpoint. Its standards apply: OpenAPI generated from code,
  and every status code documented.
- **Code:**
  - new `projects` package (model, repository, service);
  - `auth` module;
  - admin CLI commands;
  - migration `0002`.
- **Configuration:**
  - `PROJECT_KEY_PEPPER` (a secret generated by `scripts/setup-local`);
  - `AUTH_FAILURE_LIMIT_PER_MINUTE`;
  - `TRUSTED_CLIENT_IP_HEADER` (unset by default; set to
    `CF-Connecting-IP` behind the tunnel).
- **Contract and client package:** this creates contract version 1. There is
  no client package yet (phase 2).
- **Depends on:** `add-owner-notifier`, for rejection alerts.
