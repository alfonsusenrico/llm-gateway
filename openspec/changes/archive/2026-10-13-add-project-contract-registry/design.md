# Design

## Context

The gateway has Postgres, a migration runner, an admin CLI with one command,
and a notifier. The owner chose (2026-10-13):

- contracts in Postgres with history;
- keys hashed with HMAC-SHA256 and a pepper;
- an admin CLI with both subcommands and an interactive menu.

See proposal.md for motivation.

## Goals / Non-Goals

**Goals:**

- A contract model that later phases extend additively without changing its
  version.
- Key handling that stays cheap and safe on a public endpoint.

**Non-Goals:**

- Grant computation (next change).
- Enforcement (phase 2).
- Multiple concurrent active keys per environment, beyond the rotation grace
  period.

## Decisions

### 1. Contract version 1 shape

```json
{
  "contract_version": 1,
  "project_id": "personal_agent",
  "display_name": "Personal Agent",
  "status": "active",
  "request": {
    "production":  {"requests_per_minute": 30, "concurrency": 4,
                    "monthly_budget_usd": "3.00", "per_call_cost_ceiling_usd": "0.05"},
    "development": {"requests_per_minute": 10, "concurrency": 2,
                    "monthly_budget_usd": "0.50", "per_call_cost_ceiling_usd": "0.02"}
  },
  "profiles": {
    "chat": {"provider": "openai", "model": "gpt-6-luna", "reasoning_effort": "low",
             "max_output_tokens": 1200}
  }
}
```

**Validation rules:**

- `project_id`: `^[a-z][a-z0-9_]{2,39}$`, immutable.
- `display_name`: 1-80 characters.
- `status`: `active` or `disabled`.
- **Request, per environment:**
  - both environments are required;
  - `requests_per_minute` from 1 to 10,000;
  - `concurrency` from 1 to 100;
  - money values are decimal strings with at most 6 decimal places, from 0
    to 1,000, and the ceiling may not exceed the budget.
- **Profiles:**
  - names match `^[a-z][a-z0-9_-]{1,39}$`, with at most 20 profiles;
  - `provider` is `openai` or `stub`;
  - `model` is a non-empty string;
  - optional `reasoning_effort`, `max_output_tokens` (1 to 128,000), and
    `temperature` (0 to 2).

**Versioning rule:**

- Unknown fields are rejected.
- Later phases add optional fields under contract version 1 (additive).
- A breaking change needs version 2 and a stated deprecation window, with no
  silent fallback.

*Rejected:* one request block shared by both environments. Development
traffic must have its own smaller grant, so local experiments cannot spend
production budget.

### 2. Storage: projects, contract versions, keys

- `projects`: the ID and current version number. This change also adds
  `weight` (default 1), a backend-owned column that the allocation change
  uses. It is not part of the contract, because it is backend policy.
- `contract_versions`: project ID, version number, the full contract as
  `jsonb`, `changed_at`, `change_note`, and the actor (`cli:<os user>`).
- **Edits** insert a new version and move the current pointer in one
  transaction, after validation. Concurrent edits are serialized with
  `SELECT ... FOR UPDATE` on the project row.
- **Loading** validates the current version. A row that fails validation (for
  example after a manual SQL edit) marks the project quarantined in memory,
  refuses its requests with `project_quarantined`, raises an `error` alert,
  and never affects other projects.
- **Reloading:** the API caches parsed contracts for 10 s. Edits are visible
  within that time without a restart.

*Rejected:*

- **JSON files on disk:** they are prone to permission and reload problems,
  and keep no history.
- **Storing only the latest contract:** it loses the audit trail the owner
  asked for.

### 3. Key format and storage

**Format:** `lgw.<env>.<key_id>.<secret>`:

- `env` is `dev` or `prod`;
- `key_id` is 12 characters of lowercase base32;
- `secret` is 43 characters of base64url (256 bits).

The fixed prefix makes leaked keys easy for secret scanners to find.

**Stored:** `key_id`, project, environment,
`HMAC-SHA256(PROJECT_KEY_PEPPER, secret)`, `created_at`, `expires_at`
(nullable), and `revoked_at`. The raw key is printed once and never stored.

*Rejected:* scrypt or another slow password hash. It adds nothing for 256-bit random secrets
and gives an attacker a per-request CPU cost to trigger.

**Pepper:**

- `PROJECT_KEY_PEPPER` must be at least 32 bytes, encoded as base64url, and
  is generated by `scripts/setup-local`.
- Losing or changing it invalidates every key. The runbook says so, and
  rotating it means re-issuing all keys.

### 4. Authentication order

1. Check the format with the regex; a malformed key returns `401
   key_malformed`, with no database lookup.
2. Throttle by source address (step 4).
3. Look up the key by `key_id`; unknown, revoked, or expired returns `401
   key_invalid`.
4. Compare the HMAC in constant time; a mismatch returns `401 key_invalid`.
5. Check the project's status: `disabled` returns `403 project_disabled`;
   quarantined returns `503 project_quarantined`.

Unknown, revoked, expired, and wrong-secret keys share the code
`key_invalid`, so a caller cannot probe which `key_id` values exist.

**Throttling:**

- Failures are counted per source address in a 60 s sliding window, per
  process. More than `AUTH_FAILURE_LIMIT_PER_MINUTE` failures (default 10)
  makes later requests from that source return `429 auth_throttled` with
  `Retry-After: 60`, even with a valid key.
- The source address is the TCP peer address. If `TRUSTED_CLIENT_IP_HEADER`
  is set (behind the Cloudflare tunnel), it is taken from that header
  instead.

**Alerts:**

- A source crossing the threshold raises a `warning` alert,
  `auth_failures_throttled`, deduplicated per source.
- Failures against a known `key_id` raise `project_key_rejected`,
  deduplicated per `key_id`.
- Alerts carry the project ID when known, never the key.

### 5. Rotation and revocation

- `rotate-key <project> --env prod [--grace-minutes N]` issues a new key. The
  old key's `expires_at` is set to now plus N minutes (default 0, meaning
  immediately), giving a running deployment time to switch.
- `revoke-key <key_id>` revokes immediately.
- Registration issues one key per environment.

### 6. Admin CLI structure

- **Subcommands** live under `llm-gateway-admin project ...`. Each prints a
  plain result and exits non-zero on failure.
- **`set-request`** takes `--env`, `--rpm`, `--concurrency`, `--budget-usd`,
  and `--cost-ceiling-usd`.
- **`set-profile`** takes `--provider`, `--model`, `--reasoning-effort`,
  `--max-output-tokens`, and `--temperature`.
- **`export <project>`** prints the current contract as JSON, without keys.
- **`import <file>`** validates the file and saves it as a new version of an
  existing project. It never creates or changes keys.
- **The menu** (no arguments) calls the same functions, re-prompts after
  invalid input, and loops until `0` or Ctrl+C. Secrets are only ever shown
  in the one-time key output.
- **Running it:** locally with `uv run llm-gateway-admin`, or on the host with
  `docker compose run --rm api llm-gateway-admin`.

### 7. Request identity in handlers

A FastAPI dependency resolves `ProjectIdentity(project_id, environment,
key_id, contract_version)` and puts `project_id` and `environment` in the log
context. Routes never read keys themselves.

## Risks / Trade-offs

- **[Risk]** Per-process throttling lets about N times the limit through with
  N API processes. **Mitigation:** acceptable at one or two processes. It can
  move to Postgres if exposure shows abuse.
- **[Risk]** A contract cache lag of up to 10 s after an edit.
  **Mitigation:** documented. Disabling a project takes effect within 10 s.
- **[Trade-off]** The contract is stored as `jsonb` plus validation in code,
  not as normalized columns. That makes version history simple and keeps
  additive fields cheap. Queries over contract fields are not needed.

## Migration Plan

- Migration `0002_projects.sql` adds `projects`, `contract_versions`, and
  `project_keys`. It is additive.
- Existing deployments: none.
- **Rollback:** drop the routes. The tables can stay.
